# Analyst Desk Memory and Privacy Policy

**Status:** Proposed for review. Adoption, implementation and independent verification remain pending.

Analyst Desk may retain relevant context for follow-up research while protecting private information. Saved memory must not override source evidence, the approved research scope, checks or human approval. This policy defines intended behaviour; it does not certify the current application.

| Record | Save trigger and permitted use |
|---|---|
| Analyst preferences | Save only through the analyst's declared action. Keep private to the verified owner; use relevant, permitted preferences within the approved scope. |
| Published notes and coverage | Update approved history only after eligible exact-note approval and confirmed portal publication. Inherit the explicitly approved owner/workspace audience; preserve note, source, review and version links. |
| Reviewed lessons | Propose from genuine development evidence. Human-review every candidate; only accepted, applicable versions may guide research. Freeze the reviewed playbook before held-out evaluation. |
| Working state and checkpoints | Retain only what the declared resume/review purpose requires. Requests, tool outputs and drafts may persist here without becoming approved history. Context trimming does not erase checkpoints. |
| Public filing sources and indexes | Cache traceable public evidence separately from private analyst context. Source availability does not make a private watchlist or research interest public. |

**Access and disclosure.** Verify owner/workspace permissions at reads, writes, retrieval, export and deletion. A typed analyst name is not identity verification. Keep private watchlists, credentials, gold answers and protected case files out of model/search/embedding requests; controlled evaluation may supply the intended test input. Disclose which necessary authorised context enters live requests; local storage does not mean local-only processing. Keep secrets outside memory, lessons, logs and Git.

**Memory controls.** Saved analyst memory off disables optional private preference/history retrieval, including indirect tool routes, and automatic derived-memory updates for that run. Reviewed-playbook use is a separate declared setting. Current-run checkpoints and portal publication remain separate operations; switching memory off neither deletes existing records nor means nothing is stored. Reconcile current permissions and deleted/withdrawn items before resuming older state.

**Correction and deletion.** Correct preferences through authorised controls. Correct published research through a linked, checked and freshly approved version. Withdrawal, deleting derived memory and deleting a run are distinct actions. Report which records/copies were removed, retained or remain pending; reconcile coverage, loaded state, indexes and restoration paths so deleted items do not silently return. Never claim complete erasure without verifying the declared scope. Portal success plus memory-sync failure remains Published; repair the derived update separately.

**Retention and evidence.** Minimise stored content. Agree category-specific retention and backup/restore handling before adoption; no fixed expiry or third-party deletion guarantee is asserted. Revalidate historical figures before comparison. Isolate evaluation records from ordinary memory/lessons and later cases. Compare memory on/off separately from lesson benefit/harm; a working toggle is not proof of improvement.

R2 owns memory engineering, with R1 domain review, R3 workflows, R4 controls, R5 verification and R6 operations. Detailed examples and implementation expectations accompany this one-page policy.
