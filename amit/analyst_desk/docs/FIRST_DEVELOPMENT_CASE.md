# First genuine development case

This walkthrough uses registered public case **KDEV017**: compare Microsoft's Item 1A risk disclosures for fiscal 2024 and 2025. It exercises evidence selection, qualified risk interpretation, independent criticism and human lesson review. It is development work, not an independent benchmark.

## Question and baseline

> Compare MSFT Item 1A risk disclosures in fiscal 2024 and fiscal 2025. Identify supported additions, removals or material changes with citations to both versions. Separate wording changes from economic changes and state when the evidence is insufficient.

Use the exact registered question, `MSFT`, and years `[2024, 2025]`. Select live research with private analyst memory and reviewed lessons both off. Keep the normal critic, table checks and source defences enabled. Do not plant an error or inject an article. The server binds this request to the public case catalogue and current SEC source fingerprint.

The existing authorized spending limits apply to planning, research, any repair and optional AI reflection together. Do not reset the ledger or release old reservations to make a case fit. Credentials, balances, complete runtime records and human confirmation text remain local and ignored by Git.

## Run and review

1. Check source/retrieval readiness and available authorization. Save a private baseline of runs, approved notes, analyst preferences, note eligibility and lesson versions.
2. Create this registered development run. Inspect the complete generated plan and its exact payload hash. Obtain the analyst's decision before research resumes.
3. Run research and the critic. Inspect the cited source passages, code checks, semantic criticism and any repairs. A provider failure is an operational problem, not a critic rejection or a reusable research lesson.
4. Present the complete resulting note. This development run cannot publish to the approved library. Record an analyst edit only when the analyst actually requests a correction to the note; do not manufacture an edit to create a lesson.
5. Reflect only on an eligible, persisted critic rejection or actual analyst edit. Bind each pending proposal to the event, output hashes and source version. Review its fixed action, explanation, applicability and counterexamples. A successful run without such an event may correctly produce no proposal.
6. Have the analyst accept or reject each exact proposal with a reason. Acceptance does not automatically apply guidance. Freeze only an explicitly selected accepted set before any later evaluation.
7. Verify the recorded provenance and confirm that the approved library, unrelated runs and analyst preferences were preserved. Commit a sanitized outcome receipt and update the step log at each completed increment.

## What to inspect

For risk comparisons, citations to selected excerpts do not establish that an entire risk was added, removed or became economically more important. Check uncertainty, conditions and negation against both versions. Original Item boundaries remain unverified in this snapshot, so retain that limitation throughout the plan and note.

The four available lesson actions are fiscal-period alignment, current-fact verification, preserved risk qualifiers and exact-evidence citation. Select a proposal only when its originating event justifies that guidance. A rule-based proposal may choose an overly broad category; rejection or a revised pending proposal is a legitimate review outcome.
